# Emergency Box Notify — KPN Hospital

Pharmacy department app for tracking emergency drug boxes: register, dispense, return, expiry alerts.

**Live app**: https://emergencyboxnotyfykpnhos.web.app  
**Deploy branch**: `claude/eloquent-heisenberg-vqrypu` (auto-deploys to Firebase Hosting on push)

---

## Architecture

### Runtime
Single `index.html` using a custom React-like wrapper called **DC Runtime** (`support.js`).
- Component class extends `DCComponent`
- `renderVals()` returns a `vals` object consumed by `{{ }}` template bindings
- `setState()` triggers re-render; `this.state` holds all UI + data state
- `this.BOXES`, `this.AUDIT`, `this.BOX_DRUGS` are mutable class properties synced from Firestore

### Firebase
- **Firestore** (compat SDK v10): real-time listeners via `onSnapshot`
- **Anonymous Auth**: required for Firestore read/write (security rules: `request.auth != null`)
- `firebase-init.js`: synchronous init, sets `window.EB_Firebase = {app, db, auth}`
- `firebase-sync.js`: all Firestore interaction via `window.EB_Sync`
- `notify.js`: expiry alert logic, LINE/email via GitHub Actions

### Data collections
| Collection | Doc ID | Key fields |
|---|---|---|
| `boxes` | box ID (`eb1`, `eb2`, …) | `dispense`, `receiver`, `mfg`, `expiry`, `nearDrug`, `preparer`, `checker`, `openedAt`, `preparedAt`, `registeredAt`, `rejectedAt`, `rejectedReason` |
| `box_drugs` | box ID | `boxId`, `drugs[]` (with `lots[]`, each drug has `verified: boolean`) |
| `audit_log` | auto-ID | `date`, `time`, `action`, `person`, `eb`, `dept`, `drug` (append-only — rules block update/delete) |
| `usage_log` | auto-ID | `boxId`, `dept`, `drugName`, `qty`, `hn`, `patientName`, `recordedAt`, `recordedTime` (append-only, paperless usage records — see below) |
| `users` | **username** (string) | `name`, `username`, `password`, `role`, `dept`, `status`, `lastLogin`, `id` |
| `app_settings/dept_pins` | fixed doc | `{ER:{hash}, WARD:{hash}, LR:{hash}}` — per-department PIN hashes for paperless usage logging |

## Critical Invariants — DO NOT BREAK

### 1. User identity key = `username`
After Firestore loads users, `uid` = Firestore doc ID = username string. The legacy numeric `id` field is unreliable — it is undefined for Firestore-loaded users.

**Always use `username` for user comparisons:**
```js
// CORRECT
users.find(x => x.username === target)
users.map(x => x.username === target ? updated : x)

// WRONG — breaks after Firestore sync (id is undefined)
users.find(x => x.id === target)
users.map(x => x.id === u.id ? updated : x)
```

`syncUsers(user)` uses `uid || user.username` as the Firestore doc ID. Do not change this.

### 2. Boxes have no `status` field
Boxes are "out" when `box.dispense && !box.receiver`. There is no `box.status === 'out'` field.

```js
// CORRECT
const isOut = b.dispense && !b.receiver;

// WRONG — always false/undefined
const isOut = b.status === 'out';
```

### 3. Anonymous auth lifecycle
- `initUsersOnly(comp)` — called from `componentDidMount`, signs in anon + starts `listenUsers`
- `initFirebaseSync(comp)` — called after login, starts boxes/audit/boxDrugs listeners
- `stopSync()` — called on logout, stops only boxes/audit/boxDrugs
- `stopAll()` — called from `componentWillUnmount`, stops everything
- `auth.signOut()` is NOT called on logout — anonymous session must persist so the users listener keeps running for next login

### 4. Seeding flow
`seedIfEmpty()` (called by `initFirebaseSync`) seeds boxes + box_drugs if collections are empty.  
`_startUsersListener()` (called by `initUsersOnly`) seeds admin to users collection if empty.  
Do NOT seed users inside `seedIfEmpty`.

### 5. `listenUsers` dedup by username
Firestore may have duplicate username docs from historical bugs. `listenUsers` deduplicates:
```js
const seen = new Set();
snap.forEach(doc => {
  const u = {uid: doc.id, ...doc.data()};
  if (u.username && !seen.has(u.username)) { seen.add(u.username); users.push(u); }
});
```
Do not remove this dedup.

## User Management Flow (admin only)

All 5 user management functions (`setUserRole`, `toggleUserStatus`, `openChangePw`, `deleteUser`, `addUser`) check `currentUser.role === 'admin'` at entry.

`addUser()` assigns a numeric `id` for legacy compatibility. After Firestore sync, `usedIds` is built from `users.map(u => u.id).filter(x => typeof x === 'number')` — this correctly handles mixed Firestore/local users.

`addUser()` guards against concurrent double-invocation with `this._addingUser` (checked synchronously before the first `await`) — without it, a double-click/double-submit could fire it twice before the first call's `hashPw`/write settled, and both calls would pass the "username doesn't exist yet" check and each locally append their own copy of the new user, showing duplicate rows until the next Firestore snapshot reconciled them.

Role hierarchy: `admin` > `pharmacist` > `technician`. `nurse` (พยาบาล/หน่วยงาน) is view-only per the RBAC chart — dashboard + box status only, never register/dispense/return. Enforced in 3 places: `go()` refuses to navigate to `'entry'` for `role==='nurse'`, the sidebar/mobile nav omit the entry item for nurses, the Detail screen's quick-action dispense/return buttons are hidden for nurses, and `submit()` itself refuses to record a transaction for a nurse as defense in depth (in case any of the above is bypassed).

History/audit log **viewing** (`screen === 'history'`) is open to every role — only **exporting** (`exportCSV`) is admin-only (`canExportCSV`), gated both by hiding the button and inside `exportCSV()` itself as defense in depth.

`setUserRole`/`toggleUserStatus`/`deleteUser`/`addUser`/`saveChangePw` all `await` their `EB_Sync.syncUsers`/`deleteUser` call and only update local `state.users`/flash success/`logAction` if it resolves — `syncUsers`/`deleteUser` in firebase-sync.js `throw` on failure (not swallow), matching the box-operation pattern above. `setUserRole`/`toggleUserStatus`/`deleteUser` also refuse (via `_activeAdminCount()`) to demote/suspend/delete the last remaining active admin — without it, two admins racing to demote each other simultaneously could leave zero admins with no in-app recovery path.

Login lockout (`_failLogin`/`_loadLockStateFor`) is scoped **per username** (sessionStorage key includes the username), not one shared counter for the whole browser — a shared ward workstation must not let one person's mistyped password lock every other username out of that device.

## Submit Flow

All 3 modes call `_syncBox(updated)` + `resetForm()` at the end.

`_syncBox(box)`: updates `this.BOXES` in memory AND calls `EB_Sync.syncBoxes(box)` for Firestore.

```
register (Stage 1, จพ.): sets mfg, preparer, preparedAt; clears checker/registeredAt, dispense/receiver, openedAt=''
register (Stage 2, เภสัชกร/admin): sets expiry, nearDrug, checker, registeredAt — box_drugs drugs[].verified=true for every drug
dispense:  sets dispense dept, dispDate, dispenser; clears receiver; if swapReturn also syncs swap box
return:    via returnBoxAndDrugsTx() atomic transaction — sets receiver, retDate, openedAt='', AND resets preparedAt/registeredAt/checker='' + box_drugs drugs[].verified=false for every drug (a returned box must go through Stage 1 restock + Stage 2 re-verify again before it can be dispensed a second time); NOT a plain _syncBox() call (see below)
```

`_syncBox()` diffs `updated` against the last-known box and only writes CHANGED fields — never resend the full object from a stale local snapshot, or a concurrent write from another device can be silently clobbered even under `{merge:true}`.

`_syncBox()` returns a promise resolving `true`/`false` (never rejects) so a caller that must not log/toast a false success can `await` it. **Any code path that calls `logAction`/`logBoxHist` after a `_syncBox`/`_syncBoxDrugs` write must `await` that write first and bail out if it resolves falsy/rejects** — logging to the append-only `audit_log` before confirming the write landed leaves a permanent false record if it failed (network drop, etc.). `submit()`'s dispense/register branches and `rejectReg()` all follow this pattern; keep it when adding new write+log call sites.

`saveEditDrugs()` (Detail screen's drug/expiry editor) is a plain overwrite of the whole `box_drugs.drugs[]` array, not a transaction — it compares `this.BOX_DRUGS[id]` against the snapshot taken when editing started (`this._bdBackup`) and refuses to save if they differ, since a concurrent `returnBoxAndDrugsTx`/`logDrugUsageTx` could have changed quantities while the editor was open. Do not remove this check or the editor can silently revert a real return/usage decrement.

## 2-Stage Registration (จพ. เตรียม → เภสัชกร ตรวจสอบ)

Registration is split into two role-gated stages instead of one single-step save:

- **Stage 1 — จัดเตรียม (Prepared)**: any user fills in mfg date, preparer name, and per-lot qty/expiry for every drug, then saves. This writes `preparedAt` (NOT `registeredAt`) and clears any prior `checker`/`registeredAt` — a box always re-enters Stage 1 when its drug data is re-prepared, even if it was previously verified. Printing the physical EB label (`printEBForm()`) happens here — the printed "ผู้ตรวจสอบ" line is left blank for the pharmacist to hand-sign after physically checking the box in Stage 2; the print gate no longer requires `regChecker`.
- **Stage 2 — ตรวจสอบ/ยืนยัน (Verified)**: **pharmacist/admin only** (`_canVerifyReg()` — checks `role === 'pharmacist' || role === 'admin'`). Reviews the จพ.-entered data read-only against the physical box/printed label, ticks a per-drug `verified` checkbox (`box_drugs.drugs[].verified`, toggled via `toggleDrugVerified()`) for **every** drug, signs `checker`, then saves — this sets `registeredAt` (now means "verified", not "prepared") and computes `expiry`/`nearDrug`.
- **`_regStage(box)`** (index.html): returns `'none'` (no `preparedAt`) / `'prepared'` (`preparedAt` set, no `registeredAt`) / `'verified'` (`registeredAt` set). This is the single source of truth for which view (`regIsEditable` / `regIsVerifyStep` / `regIsLocked` / `regIsVerifiedLocked`) the register screen shows.
- **Hard-blocked from dispense**: `_resolveDispEB()` and the dispense box-chip list only include boxes with `registeredAt` set — a `'prepared'`-only box (จพ. done, not yet verified) cannot be dispensed under any circumstance, not just a warning.
- **Locked view**: a technician (or any non-verifier) viewing a `'prepared'` box sees a read-only "รอเภสัชกร/แอดมินตรวจสอบ" banner instead of the form — they cannot re-edit Stage 1 data or attempt Stage 2 while verification is pending.
- **`'verified'`-stage boxes are also locked, read-only** (`regIsVerifiedLocked`) — selecting an already-verified box from the landing/chip picker must NOT fall through to `regIsEditable` (the Stage 1 form). `regIsEditable` is defined as `!regIsVerifyStep && !regIsLocked && !regIsVerifiedLocked`, not merely "not prepared" — a 'verified' box used to satisfy that weaker condition, letting anyone silently re-open and re-submit Stage 1 against an already-checked box and wipe its `registeredAt`/`checker`/per-drug `verified` data with zero warning. The only way back to Stage 1 from `'verified'` is the confirm-gated `adminReopenReg(boxId)` (mirrors `rejectReg()`: clears `preparedAt`/`registeredAt`/`checker`, unticks every drug's `verified` flag, logs to `audit_log`/box history) — gated by `_canVerifyReg()` (pharmacist/admin, the same role check as verifying a box in the first place — despite the method's name, it is intentionally NOT admin-only), not by `technician`. Do not add a technician path that bypasses this confirm dialog.
- Do not add a `.par`-based or per-lot verification granularity — verification is intentionally **per-drug**, not per-lot.
- **Reject-to-edit**: in Stage 2, the pharmacist/admin can call `rejectReg(boxId, reason)` instead of verifying — clears `preparedAt`/`registeredAt`/`checker` and every drug's `verified` flag (mfg/preparer/drug data is left as-is so จพ. can see and fix it), logging the optional reason to `audit_log`/box history. This is the only way back from `'prepared'` to `'none'` short of the box being dispensed.
- **`rejectedReason`/`rejectedAt`** persist through the `'none'` stage (unlike `preparedAt`/`registeredAt`/`checker`, which `rejectReg()` clears) so จพ. sees why the box came back — shown as a red banner on the Stage 1 form and in a dashboard-wide "กล่องถูกตีกลับ" list. Stage 1 submit clears both once จพ. re-submits the fix — do not let them survive past the next `preparedAt`.
- **Dashboard "pending verification" banner**: the dashboard lists every `'prepared'`-stage box (จพ.จัดเตรียมเสร็จแล้ว รอตรวจสอบ) with a one-click jump into its register/verify view (`pendingVerifyBoxes` in `renderVals()`), so a pharmacist doesn't have to click through every EB chip to find pending work. Visible to all roles; only pharmacist/admin can actually act on what it links to.
- Selecting a box in the register EB-chip picker prefills `regMfg`/`regPreparer` from the box's persisted values **only if that box already has them** (e.g. reopened after a Stage 2 reject) — a brand-new (`'none'`-stage) box keeps whatever the user already typed, so a จพ. preparing several boxes in a row doesn't lose their own name each time they switch boxes.
- `selectRegBox()` must NOT set `this._regTouched = true` — it only marks a genuine edit (typing/ticking/printing) as dirty. It used to set this unconditionally on every box switch, which combined with the prefill above meant simply viewing any already-registered box (i.e. almost any real box) made `go()`/`go2()`/the "ล้างฟอร์ม" button's dirty-check fire on every subsequent navigation attempt for the rest of the session. The three dirty-checks (`go()`, `go2()`, `resetForm`'s clear-button handler) key off `this._regTouched` alone for this reason — do not reintroduce a raw `regMfg`/`regPreparer`/`regChecker` truthiness check into them.
- **Register screen has a landing view**: `state.regLanding` (default `true`) gates `regShowLanding`/`regShowForm` — before picking a box, จพ./เภสัชกร see an overview grid (`regLandingCardsEl`, one card per box built directly in `renderVals()`) showing each box's real stage (⚪ none / 🟡 prepared / 🟢 verified / 🔴 rejected) plus preparer/rejection-reason context, so they don't have to click through every EB chip to find work. Clicking a card calls `selectRegBox(id, {force:true})`, which also sets `regLanding:false`. A currently-dispensed-out box is shown but disabled (can't be selected — registering an out box is invalid anyway). `go2('register')` resets `regLanding:true` on every mode switch into register, and `resetForm()`'s register branch sets it back to `true` after a submit, so finishing one box returns to the overview instead of auto-jumping into some other box. The "← กลับไปเลือกกล่อง" back button (`regBackToLanding`) reuses the same `_regTouched`-gated confirm-before-leaving pattern as `go()`/`go2()`. The EB-chip strip (`regEBSelectEl`) still exists inside the form view itself for quick switching between boxes without going back to the landing.
- **Landing cards sort by urgency, not box order**: rejected (0) > prepared/awaiting-verification (1) > none (2) > verified (3) > dispensed-out (4, regardless of underlying stage — can't be acted on right now anyway). `regLandingSummaryEl` shows a count-per-status chip row above the grid. A rejected card also gets a `pulseRed` animation — do not remove either; both exist specifically so a box needing urgent action can't get lost among boxes that don't.
- **Verified box landing card subtitle shows the checker, not just the preparer** — a `'verified'`-stage card's primary subtitle is `ตรวจสอบโดย {checker}` (with `จัดเตรียมโดย {preparer}` as a secondary line), NOT the same `จัดเตรียมโดย {preparer}` text used for `'prepared'` cards. Do not collapse this back to one shared subtitle string — a pharmacist's sign-off must be visible on the card without opening the box. The checker line uses `mkPickerCard`'s `subtitleAccent: true` (bold, colored to the badge's status color, ✅ icon) so it visually outranks the muted secondary preparer line (📝 icon) — this was a deliberate follow-up fix after both lines first shipped in the same flat gray weight, making the pharmacist's sign-off easy to miss at a glance.
- **Dispense and return modes have their own landing/box-picker grids too**, mirroring register's (`state.dispLanding`/`state.retLanding`, default `true`, gate `dispShowLanding`/`dispShowForm` and `retShowLanding`/`retShowForm`). All 3 modes share one card-shell builder (`mkPickerCard`, defined once in `renderVals()`, used by `regLandingCardsEl`/`dispLandingCardsEl`/`retLandingCardsEl`) — keep new landing UI changes in that one shared function rather than forking the styling three ways.
  - **Dispense landing**: only a verified (`registeredAt` set) + in-stock box is selectable (🟢 พร้อมจ่าย); a `'prepared'`-only box is shown disabled (🟡 รอตรวจสอบ) and an already-dispensed-out box is shown disabled with its department (📤 จ่ายออกอยู่แล้ว). Selecting calls `selectDispBox(id)`, which re-validates eligibility itself (not just trusting the disabled attribute) before setting `dispEB`/`dispLanding:false`.
  - **Return landing**: only a dispensed-out box is selectable, badged with its days-out count colored the same >30d/>15d/else thresholds as `retDaysOutColor` (so the most overdue boxes visually stand out, with a `pulseRed` animation past 30 days); an in-stock box is shown disabled (✅ อยู่ในห้องยา). Selecting calls `selectRetBox(id)`, same re-validate-before-select pattern as `selectDispBox`.
  - **Dispense landing's near-expiry warning line** (`subtitle2` on a dispensable card) is deliberately given its own warning color (`subtitle2Color: '#E03E3E'`/`'#D97706'`) instead of inheriting `badge.color` — a dispensable box's badge is green ("พร้อมจ่าย"), and a warning line rendered in that same green would read as reassuring instead of cautionary. Do not let a warning/caution line default to `badge.color`.
  - `mkPickerCard`'s hover elevation is tinted with the card's own `badge.color` (via a small local `hexToRgba` helper) rather than one flat gray shadow for every card — keep this when adding new card variants; it's a deliberate visual-polish detail, not incidental.
  - `go2(formMode)` resets the landing flag for whichever mode is switched into (`regLanding`/`dispLanding`/`retLanding`), and `resetForm()` resets the current mode's landing flag back to `true` after a submit — so finishing one dispense/return also returns to that mode's overview, matching register's existing behavior.

## Paperless Usage Logging (QR public page)

Scanning a box's QR code (`?view=box&id=...`, no login) shows real-time box/drug data AND, while the box is dispensed-out, an "เปิดใช้งานกล่อง" button that lets ward staff log drug usage (drug, qty, HN, patient name) without a paper form.

- **Identity**: a per-department PIN (`ER`/`WARD`/`LR`), hashed with the same `hashPw()` SHA-256 helper as user passwords, stored in `app_settings/dept_pins`. Admin sets/rotates PINs from the Notify/Settings screen (`saveDeptPins()`) — the admin UI never displays an existing PIN, only whether one is set (`deptPinsSet`).
- **PIN check is client-side only** (fetches `dept_pins`, hashes the input, compares) — same trust model as the rest of the anonymous-auth architecture. It gates the UI, not Firestore rules; anyone with Firestore access already has write access to these collections. Do not treat it as a hard security boundary.
- **`openedAt`**: set once per dispense cycle, the first time `logDrugUsageTx()` runs on a box with no `openedAt` yet. Cleared to `''` on register and on return (`returnBoxAndDrugsTx`'s `boxFields` always includes `openedAt: ''`) — do not let a stale `openedAt` survive into the next cycle.
- **Return also forces re-verification**: `returnBoxAndDrugsTx`'s `boxFields` includes `preparedAt: '', registeredAt: '', checker: ''` and the transaction itself sets `verified: false` on every drug — a box that was just dispensed and used is no longer guaranteed full/verified, so `_regStage()` drops it back to `'none'` and `_resolveDispEB()` correctly excludes it from the dispense list until จพ. restocks (Stage 1) and a pharmacist re-verifies (Stage 2) again. Do not remove this — without it, a partially-used box could be re-dispensed immediately after return with no restock/recheck at all.
- **`logDrugUsageTx(boxId, dept, drugIdx, lotIdx, qty, hn, patientName, recordedAt, recordedTime)`** (firebase-sync.js): one atomic transaction — verifies the box is still out, verifies `qty` does not exceed the lot's current quantity (rejects with `INSUFFICIENT_QTY` rather than clamping), decrements `box_drugs`, sets `openedAt` if unset, and appends a `usage_log` entry. Mirrors `returnBoxAndDrugsTx`'s pattern so concurrent usage entries from different devices compose correctly instead of one clobbering another.
- **`submitPubUsage()`** (index.html) also writes a `cat: 'usage'` entry to `audit_log`/box history after a successful `logDrugUsageTx` — do not remove this. `usage_log` alone is invisible to the admin's main Audit screen/export, so without this a drug-administration event (exactly what an admin most needs to audit) would have no trace outside the separate usage-log panel. There's no individual login on the public page (only a per-department PIN), so the entry is attributed to `หน่วยงาน {dept} (สแกน QR)`, not a person's name.
- **Real-time "box opened" LINE alert**: `logDrugUsageTx`'s transaction returns `openedNow: !boxData.openedAt` — `submitPubUsage()` fires `_triggerUsageAlert()` only when this is `true` (the FIRST usage entry of a dispense cycle), never on every subsequent lot logged within the same cycle, or the pharmacy would get one LINE message per drug instead of one per box-opening event. Goes through a dedicated GitHub Actions workflow (`usage-alert.yml` → `.github/scripts/usage-alert.js`, `workflow_dispatch` triggered) rather than sending from the client directly — the MOPH Notify `client-key`/`secret-key` live only as GitHub Actions secrets and must never reach the public, unauthenticated QR page. `_triggerUsageAlert()` loads the GitHub PAT fresh via `EB_Notify.loadGithubPAT()` (same `app_settings/notifications` doc already documented as world-readable under this app's anon-auth trust model, so reading it from this page isn't a new exposure) and reuses the same `workflow_dispatch` + PAT pattern as the Notify screen's `triggerGHActions()`. The message is a plain LINE text (not a Flex card like the daily report — a one-line operational ping, not something to review) and **deliberately excludes HN/patient name** — the LINE group it posts into may be seen by more people than need patient identifiers to act; HN/patient name stay recorded in `usage_log` as before, just not repeated into a wider channel. Fire-and-forget like every other KPI/notify side-effect in this app — a failed alert must never surface an error on the public page or delay the success message the ward actually needs to see.
- **`listenUsageLog(boxId, cb)`** filters by `boxId` only (no `orderBy`) — sorts client-side. Adding `.orderBy()` to that query would require a composite Firestore index that does not exist; do not add it without also creating the index.
- The paper label workflow still exists side-by-side: `regSkipPrint` (a checkbox on the register form) bypasses the `regPrinted` validation gate so a pharmacist can choose paper or paperless per registration — do not remove `printEBForm()`/the print button.
- **`printEBForm(layout)`** defaults to `'landscape1'` (A4 landscape, form on the left half sized as A5, right half blank, cut down the middle) — prints onto ordinary A4 paper, the one paper size every printer reliably supports. Direct-to-A5 printing (`'a5'` portrait, `'a5l'` landscape with a two-column `formHTMLLandscape` layout) was tried as the default first, but real hardware (a cheap HP LaserJet 103/107) could not handle a true A5 page correctly in either orientation — portrait printed rotated 90° onto A4, landscape overflowed onto a second page — because its driver doesn't properly support A5 as a distinct paper size. Both A5 modes are kept in the function as options for printers that *do* support A5. This HTML-based function itself is still kept in the codebase (directly callable, still tested) — but is **no longer wired to the print button**; see `printEBFormPDF()` below.
- **The print button calls `printEBFormPDF()`, not `printEBForm('landscape1')`** — an HTML page's `@page` CSS size is only a hint the browser/printer driver can (and did, in practice) interpret differently across different computers, causing the exact same printout to come out a different physical size depending on which machine printed it. `printEBFormPDF()` generates a real PDF file instead (via `jsPDF` + `jspdf-autotable`, vendored at `/vendor/jspdf.umd.min.js` and `/vendor/jspdf.plugin.autotable.min.js`, lazy-loaded only when the print button is clicked so they never block initial page load) — a PDF's page size is baked into the file itself, which every PDF viewer's print dialog honors far more consistently than an HTML page's CSS hint. It replicates the exact same physical layout as `'landscape1'` (A4 landscape, content in the right half sized as A5, left half blank, cut down the middle) since that's the only layout ever proven to print correctly on the deployed hardware — do not switch it to a true A5 page size without confirming the target printer actually handles A5 correctly first (same caveat as above).
  - **Thai text requires an embedded font** — unlike a webpage (which borrows whatever font is already loaded/installed), a PDF must have its font data embedded directly in the file. `/fonts/Sarabun-Regular.ttf` and `/fonts/Sarabun-Bold.ttf` are Google's Sarabun font (via the `@fontsource/sarabun` npm package's `latin`+`thai` unicode-range subsets) merged into single files with `fontTools.merge` — the two subsets alone are each missing either all Latin/digit glyphs or all Thai glyphs; do not swap in an unmerged single-subset font file, half the form's text (either the Thai labels or the English drug names/dates) would silently fail to render.
  - `_ensurePdfLibs()` checks `window.jspdf.jsPDF.API.autoTable` (not just `window.jspdf`) before deciding whether to load the autotable plugin script — jsPDF and the autotable plugin are separate scripts that must load in that order (autotable patches jsPDF's prototype on load), and this check lets the function correctly skip re-loading either one if it's already present from a previous print in the same session.
  - `_getPdfFonts()` fetches + base64-encodes both font files **once per session** (cached on `this._pdfFontsCache`), not once per print — re-fetching ~90KB of font data on every single print click would be wasteful.
  - `sw.js`'s cache-first regex includes `ttf` (alongside `js|svg|css|png|jpg|woff2?`) so these font files, once fetched, are cached the same way `/vendor/*.js` already is — none of this is in `PRECACHE_URLS` (the install-time precache list) since it's only needed the moment someone actually prints, not on every page load.
- **Registration stage badge**: the public page computes `this._regStage(pubBox)` and shows a real-time badge next to the in-stock/out-of-stock one — 🟡 "รอเภสัชกรตรวจสอบ — ยังไม่พร้อมจ่าย" for `'prepared'`, 🟢 "ยืนยันแล้ว — พร้อมจ่าย" for `'verified'`, nothing for `'none'`. The registration info card also shows `registeredAt` ("ยืนยันเมื่อ") when set. Without this, a box scanned mid-Stage-2 review would show mfg/preparer data with an empty checker field and no indication it isn't finalized yet — do not gate this card on `pubBox.mfg` alone as if any mfg value means the box is ready.

## Common Pitfalls

- Do not add `x.id`-based user lookups — `id` is legacy and unreliable after Firestore sync
- Do not add `box.status` comparisons — the field does not exist
- Do not call `auth.signOut()` on logout
- Do not call `listenUsers()` from `initFirebaseSync` — it's already subscribed from `initUsersOnly`
- Do not call `initUsersOnly` more than once without first calling `stopAll` — it guards with `if(_usersUnsub)return`
- Do not hardcode dates anywhere in state initialization — use empty string `''`
- `currentUser` is updated in state via `setState` after login. To detect "self" row in user table: `u.username === st.currentUser.username`
- Do not add `.orderBy()` to the `usage_log` Firestore query — it needs a composite index that doesn't exist; sort client-side instead
- Do not call `.get()` without `{source:'server'}` on any completeness-critical one-time fetch (KPI dashboard, CSV/PDF exports, box history) — the default silently resolves empty from an empty local cache when the backend is unreachable, indistinguishable from genuinely-zero data with no error shown anywhere
- Do not call `logAction`/`logBoxHist` before confirming a `_syncBox`/`_syncBoxDrugs` write actually succeeded — always `await` the write and check its result first (see Submit Flow above); logging success on a failed write leaves a permanent false record in the append-only `audit_log`
- Do not let a new drug-administration event skip `audit_log` — writing only to `usage_log` (or only `box_drugs`) creates a blind spot in the admin's main audit trail for exactly the kind of event (who gave what drug, when) that most needs to be auditable
- Do not let `openedAt` survive past a box's dispense cycle — always reset it to `''` alongside `dispense`/`receiver` on register and return
- Do not treat the department PIN as a real security boundary — it's a client-side UI gate only, consistent with this app's anonymous-auth trust model, not a Firestore rules restriction
- Do not dispense a box whose `registeredAt` is unset, even if `preparedAt` is set — `'prepared'` (จพ. done) is not the same as `'verified'` (เภสัชกร/admin checked); dispense eligibility must check `registeredAt`, not `preparedAt` or `mfg`/`expiry` presence
- `go(screen)`'s nurse block on `'entry'` returns `false` explicitly (not a bare `return;`, which yields `undefined`) — call sites like the dashboard's `goVerify`/`goFix` shortcuts and the dispense/return quick-actions check `this.go('entry') === false` to bail before also calling `go2()`/`setState()`/`selectRegBox()`; a bare `return` would make that check silently no-op since `undefined !== false`
- `_syncChipStates()` must NOT silently reassign `state.regEB` to a different box when `this._regTouched` is true (an unsaved Stage 1/2 edit is in progress) — only the `regEB` box leaving in-stock (e.g. dispensed from another device) invalidates `regPrinted`; the box switch itself is skipped so in-progress preparer/checker/lot data isn't submitted against the wrong box. `validateForm()` already blocks submitting a dispensed-out box, so surfacing that error is safer than a silent swap
- `_syncBoxDrugs(boxId, drugs)` returns a promise resolving `true`/`false` (mirroring `_syncBox`, never rejects) and rolls `this.BOX_DRUGS` back to the pre-write value on failure — callers (`saveEditDrugs()`, Stage 1/2 register submit) must `await` it and bail (stay in edit mode, no success flash, no `logAction`/`logBoxHist`) when it resolves `false`, same as the `_syncBox` await+check pattern above
- `saveEditDrugs()` (Detail screen's drug/expiry editor) awaits and checks both `_syncBoxDrugs` and `_syncBox` before exiting edit mode, flashing success, or logging — on failure it stays in edit mode so the user's typed changes aren't lost and no false record lands in `audit_log`
- Dashboard `pendingVerifyBoxes`/`rejectedRegBoxes` (the "pending verification"/"rejected" shortcut cards) are computed as empty arrays for `role === 'nurse'` — without this a nurse could reach the register/entry screen via these dashboard shortcuts despite `go()`, the nav, and the Detail quick-actions all correctly blocking that path elsewhere. Their `goVerify`/`goFix` handlers also check `if (this.go('entry') === false) return;` as defense in depth
- Do not let Stage 1 (จพ.) submit set `registeredAt` or require `regChecker`/per-drug `verified` — those are Stage 2 (เภสัชกร/admin) only
- Do not let `rejectedReason`/`rejectedAt` survive past the box's next Stage 1 submit — always reset them to `''` alongside `preparedAt` there, or a stale rejection banner keeps showing on a box จพ. already fixed
- Do not let a returned box keep `registeredAt` set — `returnBoxAndDrugsTx` must always reset `preparedAt`/`registeredAt`/`checker` and every drug's `verified` flag, or a partially-used box could be re-dispensed immediately with no restock/recheck
- Selecting a box for the register screen (chip click OR the dashboard "pending verify"/"rejected" jump links) must go through `selectRegBox(id, opts)` — it's the only place that correctly prefills `regMfg`/`regPreparer` from the persisted box and refreshes `state.boxDrugs[id]` from `this.BOX_DRUGS` (never from `state.boxDrugs[id]` itself, which can hold a stale copy). Do not set `regEB` via a bare `setState()` from a new call site.
- `resetForm()`'s register branch must reset `boxDrugs: null`, never a pre-blanked copy of some guessed "next" box — it has no way to know if that guess is the box จพ. just submitted (very likely, since box order never changes), and blanking its lot expiry there would show an empty table for data that was actually saved correctly.
- Stage 2 (`submit()`'s verify branch) and `rejectReg()` must read drug/lot data from `this.BOX_DRUGS[id]`, never `state.boxDrugs[id]` — Stage 2 is read-only over lot data (only `verified` is locally toggled), so persisting from a stale local buffer risks silently overwriting real expiry data with blanks. `regNearISOof(id, BDOverride)` takes an optional override for exactly this reason — pass `this.BOX_DRUGS` explicitly rather than relying on its default state-first fallback.
- `submit()`'s register Stage 1 and Stage 2 branches, and `rejectReg()`, each fire `_syncBox()` and `_syncBoxDrugs()` together (Stage 1/2 via `Promise.all`, `rejectReg()` sequentially) — ALL must check the success of BOTH writes, not just `_syncBox`'s. Destructuring only `const [xOk] = await Promise.all([...])` or discarding the second call's result entirely silently ignores a `_syncBoxDrugs` failure, flashing success and logging to `audit_log` even though the drug/verified data never actually saved.
- `doLogin()` must clear the lockout/attempts counters via `this._lockKey(u.username)`/`this._attemptsKey(u.username)` (the same per-username-scoped keys `_failLogin`/`_loadLockStateFor` read/write), never the bare literal strings `'eb_lockout'`/`'eb_attempts'` — those literals were never written to by anything, so clearing them on successful login was a silent no-op that left the real per-username counter un-reset, letting stale failed-attempt counts from earlier in the session cause a premature lockout on a later login.
- `reset-firestore.js` (the `reset-data.yml` Action) must clear `usage_log` alongside `audit_log`/`boxes`/`box_drugs` — since `boxes`/`box_drugs` reseed with the same fixed IDs (`eb1`, `eb2`, …) after a reset, leaving `usage_log` unclearned means the next box registered under a recycled ID still shows old patient HN/name/usage entries from before the reset in its usage-log panel.
- The GitHub PAT (Settings screen, used to manually trigger `daily-notify.yml`) is stored in `app_settings/notifications` in Firestore, which — per this app's anonymous-auth trust model — is readable by anyone who opens the site URL, even without ever logging into the app. This is an accepted trade-off (see the UI's inline warning next to the PAT field), not a bug to silently "fix" by moving storage — but it means the PAT MUST be a fine-grained token scoped to only this repo + `Actions: Read and write`, never a classic PAT with full repo/account access. Do not remove or water down the inline warning telling the admin this.
- The `<head>` `<script>` tags for React/ReactDOM/Firebase-compat/support.js/firebase-init.js/firebase-sync.js/notify.js all carry `defer` — this is safe specifically because support.js's own boot (`__dcBoot`) is already gated on `DOMContentLoaded`/`readyState`, and deferred classic scripts execute in strict document order right before `DOMContentLoaded` fires — so removing `defer` from any one of them (or reordering them) risks nothing changing observably, but adding `async` to any of them WOULD break execution order (async scripts execute whenever they finish downloading, not in document order) — do not change `defer` to `async` on these.
- The public QR-scan box page (`?view=box&id=...`) footer must keep the "จัดทำโดย ภก.อนัส มะยีแต เภสัชกร รพ.กรงปินัง" credit line — it's the deployed system's attribution, shown to every ward/department that scans a box's QR code.
- `doLogin()` guards with a synchronous `this._loggingIn` flag checked before its first `await` (`hashPw()`), mirroring `addUser()`'s `_addingUser` guard — without it, a double Enter-press/double-click while the SHA-256 hash is still resolving passes all the same checks twice and both invocations reach `window.EB_Sync.initFirebaseSync(this)`, attaching duplicate `boxes`/`audit_log`/`box_drugs` listeners; every subsequent Firestore change then fires two `setState` calls (double `_syncChipStates()`, double expiry-banner checks) until the next logout. The flag must be reset on every early-return path after it's set (wrong/suspended user, bad password) as well as on success, or a failed login attempt would permanently lock out all future logins in that session.
- `saveDeptPins()` must `await` + `try/catch` (or equivalent) `window.EB_Sync.syncDeptPins()`, same as every other admin write path (`setUserRole`/`toggleUserStatus`/`deleteUser`/`addUser`/`saveChangePw`) — `syncDeptPins()` re-throws on failure like the others, so an un-caught `await` here becomes an unhandled promise rejection with zero user-visible feedback: the admin just sees the save button silently do nothing.
- **`_isFormDirty(mode)`** is the single source of truth for "does this mode (register/dispense/return) have an unsaved edit right now" — used by the clear-form button, `dispBackToLanding`/`retBackToLanding`, `go()`'s leave-entry-screen guard, and `go2()`'s mode-switch guard. It must NOT compare `dispDate`/`retDate` against today when they're still `''` (unset, per the "never hardcode dates in state init" rule) — an unset date is not itself an edit, and comparing it unconditionally would falsely flag the very first entry into a mode (before `go2()`/login have ever populated it) as dirty.
- `_syncChipStates()` must NOT silently reassign `state.retEB` (and clear `state.retDrugUsage`) when the currently-selected return box leaves the "out" list while `_isFormDirty('return')` is true — mirrors the existing `regEB`/`_regTouched` protection. Without this, another device returning the same box mid-edit would silently zero out a paperless per-lot usage entry the user was still typing and swap the return form to a *different* box with no warning at all; `validateForm()` already surfaces "box no longer out" as an error, which is safer than a silent switch.
- `go()`'s "leave without saving?" dirty-check and `go2()`'s mode-switch dirty-check were originally register-only (`_regTouched`) — both now call the shared `_isFormDirty(this.state.formMode)` so navigating away from (or switching out of) a dirty dispense/return form warns the same way leaving a dirty register form already did. `go2()`'s mode-switch `patch` unconditionally blanks `retDrugUsage`/`swapRetDrugUsage` on every call, so without this guard switching modes via the stepper while either buffer held unsaved data silently discarded it.
- **Print label PDF vendored assets** (`/vendor/jspdf.umd.min.js`, `/vendor/jspdf.plugin.autotable.min.js`, `/fonts/Sarabun-Regular.ttf`, `/fonts/Sarabun-Bold.ttf`) are lazy-loaded only when `printEBFormPDF()` is invoked (the print button's handler) — do not move their `<script>`/preload tags into `<head>`, that would reintroduce the ~490KB payload into every page load this was specifically designed to avoid. `_ensurePdfLibs()` must check `window.jspdf.jsPDF.API.autoTable` (not just `window.jspdf`) since jsPDF and the autotable plugin are separate scripts that must load in that exact order.
- **`this.TODAY` is anchored to `Asia/Bangkok`'s calendar day**, not the device's raw local timezone (same `toLocaleString('en-US',{timeZone:'Asia/Bangkok'})` trick `notify.js`'s `todayBangkok()` already used) — before this fix the two disagreed by exactly one day whenever a workstation's OS/browser clock wasn't set to Bangkok time (a real risk in mixed hospital IT — a UTC-configured machine, a laptop brought from abroad), right around Bangkok midnight: a lot could be accepted/rejected as "already expired" a day off from what the dashboard's near-expiry count said, and `daysLeft` in the alert banner could differ by ±1 from what register/detail screens computed for the same lot. Do not revert `get TODAY()` back to plain `new Date()`.
- **A terminal `onSnapshot` error must set `state._syncError`**, surfaced app-wide as a persistent "real-time sync lost, refresh" banner (`hasSyncError`/`reloadPage` in `renderVals()`) — `firebase-sync.js`'s `_onListenerError()` helper does this for `listenBoxes`/`listenAudit`/`listenBoxDrugs`/`_startUsersListener`. The Firestore SDK's `onSnapshot` error callback only ever fires for *terminal* errors (transient network blips are retried internally and never reach it) — once it fires, that listener is dead for good with no automatic resubscribe anywhere in this codebase. Before this fix only `startPublicSync` (the public QR page) had an equivalent flag (`_publicLoadError`); the authenticated app would silently freeze `BOXES`/`AUDIT`/`BOX_DRUGS`/`users` at their last known value while every screen kept rendering as if fully live, with zero indication anything had stopped syncing.
- **`listenBoxes()`'s callback must also recompute `expiryAlerts`**, not just `listenBoxDrugs()`'s — a plain dispense/return/register write only touches the `boxes` collection (no `box_drugs` write happens in the same action), so without this the dashboard's near-expiry alert list kept showing a box's pre-write department/location context until some *unrelated* `box_drugs` write anywhere in the system happened to trigger the other listener's recompute (could be minutes to hours later). Both listeners now independently recompute `expiryAlerts` off `this.BOXES`/`this.BOX_DRUGS` (whichever is fresher at the time either fires) so the alert list's dept/location context can never lag behind a box-only write.
- **`listenAudit()`'s live listener is deliberately capped at the 500 most-recent docs** (`orderBy('date','desc').limit(500)`) to keep the real-time History/dashboard view light — but that means selecting a fiscal-year or custom date-range filter reaching further back than that window would silently show (and, worse, CSV-export) INCOMPLETE data with zero indication anything was cut off, once total `audit_log` docs exceed 500 (easily reached within weeks of real hospital use). `_fetchCompleteAuditRows(preset, dateRange)` runs a one-time (non-realtime) `fetchAuditRange()` query for `'fiscal'`/`'custom'`/an-already-at-the-cap `'all'` preset (never for `'today'`/`'7days'`/`'month'`, which can't plausibly exceed 500 docs for this box count) and falls back to the in-memory capped array with a flashed warning if the fetch fails. `exportCSV()`/`adminExportCSV()` both call this before building their CSV — **CSV export must always be guaranteed complete** since it's the compliance/audit-critical path; do not revert either export to read straight from the capped `filtered`/`_adminFiltered` arrays. The live on-screen view still honors the 500-doc cap (its footer disclaimer says so) — that's an accepted, visible trade-off, not a silent one.
- **Known, accepted narrow-race limitations** (found during a Firebase-integrity audit, not fixed — the fix would require a bigger structural change than the actual risk warrants): (1) `saveEditDrugs()`'s concurrent-edit guard (`_bdBackup` vs `this.BOX_DRUGS` comparison) is checked synchronously *before* its own `await`ed write — a real concurrent `returnBoxAndDrugsTx`/`logDrugUsageTx` landing in that sub-second gap is not caught, since the guard only detects changes that happened *before* save was clicked, not during the save itself. (2) `_activeAdminCount()`'s "keep ≥1 active admin" guard is a client-side, non-transactional check — if there are exactly two active admins and each simultaneously demotes/suspends/deletes the *other* before either's listener picks up the other's in-flight write, both checks can independently pass and both writes succeed, leaving zero active admins. Both would require converting a plain `_syncBox`/`_syncBoxDrugs`-style write into a real Firestore transaction to close properly — flagged here rather than fixed silently so a future contributor doesn't assume these paths are airtight.
- **`fetchUsageLogRange()`/`_fetchCompleteUsageRows()` mirror the audit_log completeness fix for the admin-wide usage_log report/CSV export** (`listenAllUsageLog` is capped at 1000 most-recent docs, no preset system — just plain `ulDateFrom`/`ulDateTo`) — any explicit date filter, or an unbounded export once already past the cap, triggers the extra one-time fetch so `exportUsageLogCSV()` is never silently missing older drug-administration records (who gave what dose to which HN, when). Same pattern, same reasoning as `_fetchCompleteAuditRows` — keep both in sync if either changes.
- **`reset-firestore.js`'s non-admin-`users` delete is chunked in batches of 400**, same as `clearCollection()` — a single unchunked `batch.commit()` over >500 docs hard-rejects (Firestore's batch-op cap), which would leave `audit_log`/`boxes`/`box_drugs`/`usage_log` already cleared while `users` silently wasn't, despite the script's closing "เสร็จแล้ว!" message claiming success.
- **`test-lifecycle.js` supports a `--cleanup-only` CLI mode**, invoked as a separate `if: always()` step in `test-lifecycle.yml` *after* the main test step — the script's own `.finally()`-based cleanup only runs if the Node process unwinds normally, which a GitHub Actions cancellation (someone clicking "Cancel workflow" mid-run) does not guarantee. Without the separate always-run step, a cancelled run could leave the throwaway `TEST-1` box permanently in production Firestore, indistinguishable from a real `EB-1`..`EB-10` box in the live dashboard/dispense/return pickers (nothing in the app filters box IDs by a naming pattern). - **A whole-system stability audit** ("ตรวจสอบความเสถียรของแอพทั้งระบบ") found and fixed the app's single biggest remaining crash-resilience gap: **no error boundary existed anywhere** in this React app — if `renderVals()` (the ~2,700-line function that computes the entire UI's data every render) ever threw for any reason, React would unmount the whole tree and white-screen the app for every user with zero recovery UI, discoverable only by someone reporting a blank page. `renderVals()` is now a thin `try/catch` wrapper around the original body (renamed `_renderValsInner()`) — on a throw, it returns `this._lastGoodVals` (the last successful render's full `vals` object, cached right before each of its two `return vals` points) with `appCrashed`/`appCrashedMessage` overlaid on top, so every other `{{ }}` binding in the template still resolves against a real, previously-valid shape (stale but never undefined) instead of risking a second crash from an under-specified fallback. Verified live: monkey-patched `_renderValsInner` to throw after a real successful render, confirmed the overlay renders correctly with the injected error message and a working reload button, instead of a blank page.

- **A follow-up stability pass** ("ตรวจสอบความเสถียรของแอพ ตรวจสอบการป้องกันแอพล่ม ตรวจสอบการเชื่อมข้อมูลผ่าน database firestore ได้อย่างครบ ไม่มีข้อมูลสูญหายกลางคัน") found one more concrete data-loss gap: **the app had no `beforeunload` guard at all** — every in-app navigation path (switching screens, switching register/dispense/return modes, the SW-update auto-reload guard) already checks `window.__ebHasUnsavedWork` before discarding anything, but a user closing the tab, hitting the browser's back button, or refreshing the page directly bypassed all of that with zero warning, silently discarding whatever was half-typed. - **The two "known, accepted narrow-race limitations" from the earlier Firebase-integrity audit are now actually closed**, per direct request to push stability further ("พัฒนาปรับปรุงความเสถียรของแอพให้เหนือชั้น สามารถทำงานได้อย่างมีประสิทธิภาพ ปราศจากปัญหา"):
  1. **`saveEditDrugs()`'s concurrent-edit guard is now inside a real Firestore transaction** (`saveEditDrugsTx` in firebase-sync.js). The old guard compared `this.BOX_DRUGS` against the pre-edit backup (`_bdBackup`) *before* its own `await`ed write — a concurrent `returnBoxAndDrugsTx`/`logDrugUsageTx` landing in that sub-second gap was never caught. The transaction now re-reads `box_drugs` fresh and does that same comparison atomically at commit time, throwing `CONCURRENT_CHANGE` if it's stale — closing the race the same way `returnBoxAndDrugsTx`/`logDrugUsageTx` already close theirs. Local `this.BOX_DRUGS`/`this.BOXES` caches are only updated after the transaction actually commits (no optimistic-then-rollback needed, since the transaction is all-or-nothing).
  2. **`setUserRole`/`toggleUserStatus`/`deleteUser`'s "keep ≥1 active admin" guard is now atomic** (`guardedAdminChangeTx` in firebase-sync.js), for exactly the case that mattered — demoting/suspending/deleting a user who IS an admin. The old guard counted `state.users` (a live-but-possibly-stale client array) *before* the write; two admins racing to demote/suspend/delete each other within the same instant could each independently see "the other one is still active" and both writes land, leaving zero admins with no in-app recovery path. The transaction re-reads every admin doc fresh via `tx.get()` on a `role=='admin'` query (deliberately not also filtering `status=='active'` in the query itself — a doc with no `status` field at all, this app's own "missing means active" convention, would silently fail to match that equality filter and undercount; "active" is decided client-side per doc after the query returns instead) and aborts with `LAST_ADMIN` if fewer than one *other* active admin would remain. The existing client-side pre-check is kept as a cheap first gate (avoids opening the confirm dialog for the obvious case) — the transaction is the real, race-proof guarantee. Non-admin targets (promoting someone, suspending a pharmacist, deleting a technician) are untouched — still the plain non-transactional `syncUsers`/`deleteUser`, since there's no admin-count invariant to protect there.

Full Firestore transaction semantics themselves rely on the same atomic-commit guarantee already proven live against real production Firestore for `returnBoxAndDrugsTx`/`logDrugUsageTx` earlier this session.
